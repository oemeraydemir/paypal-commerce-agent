## 2. F1 — Mobile deep-link blanking: root cause (exact lines)

`checkout.ts` builds an HTML return page whose `<head>` carries a CSP-nonce'd
inline `<script>` (line 48). The script body (lines 49–56):

```
49  if (/Android|iPhone|iPad|iPod/i.test(navigator.userAgent)) {
50    window.location.replace(${scriptAppLink});          // custom scheme
51  } else {
52    window.location.replace(${scriptWebLink});           // "/?paypal=…&token=…"
53  }
54  window.setTimeout(function () {
55    document.getElementById('fallback-message').hidden = false;
56  }, 1200);
```

- `${scriptAppLink}` (line 31, `JSON.stringify(appLink)`) is the custom scheme
  `paypalcommerceagent://checkout/<status>?token=…`.
- The only *web* fallback is the static link at **line 65**:
  `<a href="${htmlWebLink}">Continue in the browser instead</a>` where
  `htmlWebLink` (line 36) is the encoded web link `/?paypal=…&token=…`.

**Mechanism:** On a mobile User-Agent with **no registered handler** for the
custom scheme (headless Chrome, or a real device without the app installed),
`window.location.replace("paypalcommerceagent://…")` performs a navigation that
the browser cannot complete. Chrome replaces the document with a "no app found"
page / blank, so the `<body>` (lines 59–67) is destroyed **before** the 1200 ms
`setTimeout` can reveal `#fallback-message`. The fallback `<a>` (line 64, also a
custom scheme) and the web fallback (line 65) then become unreachable.

**Elimination proof (from `mobile_isolate.cjs`, already run in 10A):**
- Variant A — JS **disabled** → `anchorCount` present, `bodyLen` ≈ 411 (HTML intact).
- Variant B — JS **enabled but `location.replace` stubbed** (no real navigation)
  → anchors present, `bodyLen` > 0.
- Variant B with **real** `location.replace(scheme)` → `bodyLen: 0`,
  `TypeError … 'hidden'` (the `getElementById('fallback-message')` returns null).

The HTML is correct; the blanking is caused solely by the destructive
`location.replace` to an unhandled custom scheme. This is **CONFIRMED**, and it
is **not** a 09D regression (the old code called `location.replace` for both
branches unconditionally; 09D only redirected the desktop branch to the web
link and added the line-65 fallback — it did not make the mobile branch safe).

## 3. `app.js` role (why it is NOT the fix site)

`app.js` only runs on the **web storefront** (`/`). Its `handleReturn()`
(lines 121–138) reads `?paypal=` from the URL, calls `history.replaceState(null,'','/')`
(line 123) — which **collapses the URL to `/`** — and renders the success/cancel
banner. It does not render the `/api/checkout/return` page; that page is
server-generated by `checkout.ts`. Therefore the mobile blanking lives entirely
in `checkout.ts`, and `app.js` requires **no change** for F1. (It was reviewed
for completeness and the 09D security checks still hold: `textContent` only,
`Idempotency-Key` sent, capture verified server-side.)

## 4. F2 / F3 — Probe & evidence defects (exact lines)

### F2 — `landedOnWebApp` is a probe defect, not an app defect
`browser_flow_check.cjs` Step 2 (lines 82–91) and Step 3 (lines 101–107):

```
83  await sleep(1500);
84  results.steps.desktopReturn = {
85    finalUrl: p.url(),
87    landedOnWebApp: /\/\?paypal=success&token=ORDER-9$/.test(p.url()),
```

The probe reads `p.url()` **after** a 1500 ms sleep. But `app.js` line 123 runs
`history.replaceState(null,'','/')` on load, collapsing the URL to `/`, so the
`$`-anchored regex fails → `landedOnWebApp:false`. The **application actually
navigated** to `/?paypal=success&token=ORDER-9` — proven by `c.navigations`
(line 30, `framenavigated`) which recorded the target, and by `bannerText`
showing the cancel/success banner only when `?paypal=` was processed. The probe
measured the wrong signal (post-hoc URL) instead of the navigation event or the
rendered storefront DOM.

**Redesign (F2):** measure `landedOnWebApp` from (a) the captured navigation
request to the web link, and/or (b) the storefront DOM after load — e.g. assert
`#catalog .prod` rendered AND `#banner` contains the expected PayPal text. The
collapsed URL is expected behavior and must not be the success criterion.

### F3 — Silent evidence gaps
`browser_flow_check.cjs` lines 73, 92, 129: `try { await p.screenshot(...) } catch {}`
— the empty `catch` **swallows** failures. This is exactly why
`10a_mobile_return.png` was never created (the blanked page threw and was
silently dropped). The separate cart-interaction step emitted only a PNG, no
JSON. **Redesign (F3):** record `errors`/`warnings` arrays, emit a JSON result
for *every* step (mobile return + cart interaction included), assert a non-blank
DOM before screenshotting, and fail loudly if a screenshot cannot be written.

## 6. Minimal fix design (F1) — described, not implemented

Constraint recap from 09D: keep mobile deep-link *capability* intact, preserve
URL-encoding of the token, preserve the desktop branch, preserve CSP (the
return page legitimately uses a nonce'd inline script — keep that), no
`innerHTML`/unsafe interpolation.

**Recommended approach (non-destructive deep link):**

1. In the mobile branch (lines 49–50), **stop** using
   `window.location.replace(scheme)`. Instead attempt the scheme via a hidden
   `<iframe src="scheme">` (does not blank the parent document), OR expose the
   deep link as a visible `<a href="scheme">Open the AI Café app</a>` button the
   user taps. Either keeps the deep-link available without auto-destroying the
   page.
2. **Reveal the web fallback immediately** — set `#fallback-message` visible at
   load (or remove the 1200 ms gate) so `Continue in the browser instead`
   (line 65, the real web link) is always reachable even when the scheme fails.
3. Leave the desktop branch (lines 51–52) and the web-link fallback (line 65)
   exactly as-is.

**Consequence for test 3:** `web-storefront.test.ts` lines 31–32 currently
assert `window.location.replace("paypalcommerceagent://…")` is present. Because
the fix removes the destructive `location.replace` for the scheme, that
assertion would break. Test 3 must be updated (not weakened) to assert the new
safe behavior — e.g. the page references the deep link via iframe/anchor **and**
the web fallback link `/?paypal=success&token=ORDER-9` is present and not
hidden. This is a justified test-only change under the 09D authorization rule.
